02Why columns compress and rows don't

Parquet and ORC aren't just "zipped CSV" — they physically regroup the data before compressing it.

03What actually differs

FormatStorage modelSchemaSplittableBest fit
CSV row-wise, plain text none — inferred every time you read it only if uncompressed interchange, human-readable, small exports
Avro row-wise, binary embedded in file; strong schema evolution (add/rename fields safely) yes — has internal sync markers write-heavy pipelines, Kafka payloads, row-level record storage
Parquet column-wise, binary embedded, plus per-column stats (min/max) for predicate pushdown yes analytics, read-heavy queries that touch few columns — Spark's default
ORC column-wise, binary embedded, plus built-in indexes (min/max, bloom filters) yes analytics on Hive-centric warehouses; near-identical use case to Parquet

Row-wise (CSV, Avro) reads and writes whole records fast — good when a job touches every column, or appends rows constantly. Column-wise (Parquet, ORC) shines when a query only needs a few columns out of many — Spark can skip reading customer_name entirely if a job only asks for SUM(gross_amount).

04Format vs. compression codec — not the same lever

Compressing changes what a format costs — measured with and without it, on the same rows.

FileSizevs. CSV

Notice uncompressed Parquet (1.62 MB) already beats compressed Avro's row layout on raw bytes, purely from being columnar — compression on top of that is a second, independent win. That's the real split: columnar vs. row-wise is a storage-layout decision; which codec (snappy / zlib / deflate / gzip) is a separate dial on top of it.

06So which one should you actually use?

For your assignment's tasks 2–4 (computing gross_amount, discount_amount, final_amount), the format you read from doesn't change the logic at all — withColumn works identically whether the source was CSV or Parquet.

But if you're writing the result back out for anything beyond that one script — a second notebook, a dashboard, a teammate's job — Parquet is the practical default: smallest on disk here, splittable, carries its schema so no one has to re-guess column types, and lets Spark skip whole columns it doesn't need. ORC does the same job and is common if your pipeline sits on Hive. Avro's advantage shows up earlier in a pipeline, not later — it's built for row-by-row writes (streaming, Kafka) where you need to add a field next month without breaking old readers.

Measured on a 50,000-row reconstruction of sales_100mb.csv's schema — pandas → pyarrow (Parquet, ORC) and fastavro (Avro), default codecs per format's common real-world setting.
