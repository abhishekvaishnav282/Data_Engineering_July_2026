PySpark assignment — architecture notes

Why PySpark?

You asked the right question: on a 50,000‑row file, pandas could compute gross_amount, discount_amount and final_amount just fine — probably faster than Spark. Here's what actually changes underneath each approach, using your sales_100mb.csv task as the running example.

01Where the data actually sits

Pandas and NumPy live inside one process. PySpark splits your file across a driver and several executors before it runs a single line.

02When your code actually runs

This is the part that trips people up most: PySpark doesn't run each line as you write it.

03Five approaches, side by side

Same dimensions, applied to every option — including the two your assignment is actually comparing.

ApproachRuns onData shapeExecutesScaling ceiling
NumPy one process, in memory array — numbers only, no column names eager, line by line whatever fits in that machine's RAM
pandas one process, in memory DataFrame — labeled columns, same as your CSV eager, line by line same — whole file must fit in RAM
SQL whichever engine runs it — Postgres, Spark SQL, BigQuery… table — rows and named columns declarative — the engine decides the plan inherited entirely from the engine underneath
RDD driver + executors, distributed opaque rows — no schema, no column names lazy — waits for an action add executors; you parse and index each row yourself
PySpark DataFrame driver + executors, distributed DataFrame — labeled columns + schema, like pandas lazy — waits for an action add executors; schema and query optimizer included

This is also exactly why your earlier RDD problems felt more manual than this one: an RDD row has no column names, so you'd write float(row[11]) * float(row[12]) instead of col("quantity") * col("unit_price"). A DataFrame gives that structure back — whether it's pandas on one machine or PySpark across ten.

05Which one, when

  • pandas — data comfortably fits in memory on one machine and will stay that way. Simplest option, no cluster overhead, usually faster for small-to-mid data like this 50k-row file.
  • PySpark DataFrame — data has outgrown, or might soon outgrow, one machine. Same column-based feel as pandas, but partitioned and lazy so it keeps working past one machine's RAM.
  • RDD — you need row-level control, or the data has no natural schema. DataFrames have replaced almost every case this used to be needed for.
  • SQL — you or your team think in queries rather than code. Runs on whatever engine sits underneath, including spark.sql() directly on a PySpark DataFrame.
  • NumPy — fast numeric math on arrays you already hold in memory, with no need for column names.

06So why does the assignment use PySpark for 50,000 rows?

Honestly — for this file size, pandas would be faster, with less code and no cluster overhead. That's not a trick; it's the real tradeoff in the table above.

The point of practicing it on 50,000 rows is that the syntax doesn't change when the file stops being small. df.withColumn("gross_amount", col("quantity") * col("unit_price")) is exactly what you'd write whether sales_100mb.csv has 50 thousand rows or 50 billion spread across 200 machines. Pandas code doesn't make that jump on its own — it needs a rewrite, or a different library entirely. PySpark is what you practice now so the jump isn't a rewrite later.
